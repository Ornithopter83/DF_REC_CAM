# 작업명

공유 인코딩 기반 녹화·송출 동시성 안정화

## 목표

단일 H.264 인코딩 결과를 MP4 녹화와 실시간 송출이 공유하면서도 각 소비자의 지연·시작·중지·실패가 서로의 수명주기에 영향을 주지 않게 한다.

## 예정 구현 범위

* A. 인코더, 녹화 sink, 송출 sink의 큐·프레임·프로세스 소유권을 정리한다. (완료: 2026-08-13)
* B. 녹화 우선 backpressure와 송출 제한 큐의 독립성을 보완한다. (완료: 2026-08-13)
* C. 송출 시작·중지 중에도 프리버퍼, 파일 분할, MP4 종료 처리가 유지되게 한다. (완료: 2026-08-13)
* D. 취소·오류·앱 종료 시 리소스 정리와 녹화 회귀를 확인하고 보완한다. (완료: 2026-08-13)

### A. 소유권 분석 결과

| 리소스 | 생성·소유자 | 전달 방식 | 종료·해제 경계 |
| --- | --- | --- | --- |
| 공유 파이프라인 | `RecordingService`가 하나만 생성·보관 | 녹화·송출 API는 `RecordingService._sync` 안에서 접근 | `RecordingService.Dispose`가 이벤트 구독을 해제한 뒤 파이프라인을 Dispose |
| 원본 카메라 `Mat` | 캡처 루프 호출자 | 파이프라인 입력에서 즉시 clone하며 호출자 원본 소유권은 이전하지 않음 | encoder 큐 소비자가 clone을 `using`으로 해제하고, enqueue 실패 시 생산자가 즉시 해제 |
| H.264 encoder | `SharedEncodedMediaPipeline` | 프레임 queue와 stdout reader를 내부 소유 | 녹화·송출·프리버퍼 소비자가 없거나 파이프라인 종료 시 입력 완료, 프로세스 종료, 남은 `Mat`, queue와 process 해제 |
| 인코딩 chunk | encoder stdout reader | 프리버퍼·녹화 sink·송출 sink가 각각 필요한 byte 배열 복사본을 소유 | 프리버퍼 제거·초기화 또는 각 sink queue 소비·폐기 후 GC 회수 |
| 녹화 sink | 공유 파이프라인 | 필수 queue로 chunk 복사본 전달 | 녹화 중지·분할·파이프라인 종료에서 queue 완료 후 MP4 FFmpeg 종료를 기다리고 Dispose |
| 송출 sink | 공유 파이프라인 | 제한 queue로 chunk 복사본 전달 | 중지·교체·실패 시 즉시 fan-out에서 분리하고 추적 cleanup 작업이 FFmpeg·queue·process를 정리 |
| 상태 이벤트 | 공유 파이프라인 | 세대가 포함된 불변 상태 값만 비동기 전달 | `RecordingService`와 coordinator가 종료 전에 구독 해제·추적 작업 완료 |

* 녹화 sink 교체와 송출 sink 분리는 encoder fan-out과 같은 파이프라인 잠금 안에서 수행하고, 오래 걸리는 FFmpeg 종료는 잠금 밖에서 처리한다. 따라서 한 chunk가 두 녹화 파일에 중복되거나 종료 중인 송출 sink로 새 데이터가 들어가는 소유권 경계는 없다.
* `RecordingService`의 fallback writer와 raw 프리버퍼는 공유 파이프라인과 동시에 활성화되지 않는다. FFmpeg 공유 경로에서는 압축 프리버퍼만 사용하고 fallback 경로에서는 `BufferedFrame`의 `Mat`을 서비스가 직접 해제한다.
* A 분석에서는 누락된 Dispose, 동일 프로세스의 이중 소유 또는 호출자 `Mat`의 소유권 이전 문제를 발견하지 않았다.
* B에서 녹화 필수 queue와 encoder frame queue의 대기 방식이 캡처·fan-out에 미치는 영향을 보완한다. C에서는 압축 프리버퍼를 녹화 sink에 주입하는 동안의 잠금과 분할 교체 불변식을 확인한다. D에서는 제한시간 종료 뒤 worker·process 해제 순서를 최종 확인한다.

### B. backpressure 분석 결과

* encoder 입력 queue는 녹화 중 필수 enqueue를 사용해 프레임을 버리지 않는다. 녹화가 없고 프리버퍼·송출만 동작할 때에는 제한 queue의 `TryAdd`를 사용해 캡처 루프가 네트워크 소비자 때문에 대기하지 않는다.
* 녹화 sink는 2,048개 chunk 제한 queue에 복사본을 필수 enqueue한다. 디스크 패키징이 실제 인코딩보다 느리면 encoder stdout reader에 backpressure를 전달해 메모리 무제한 증가 대신 녹화를 우선 보존한다.
* 송출 sink는 별도 128개 제한 queue에 무대기 `TryAdd`한다. queue 포화, 프로세스 실패 또는 종료 경합 시 해당 송출 sink만 fan-out에서 분리하고 `rtmps_publish_failed`를 보고하며 녹화 sink와 encoder는 유지한다.
* 송출 queue와 녹화 queue 사이에는 공유 컬렉션이나 상대 queue 대기가 없다. 송출은 녹화 enqueue를 호출하지 않고, 송출 cleanup도 녹화 process·queue를 닫지 않는다.
* 현재 경계가 목표한 녹화 우선·송출 비차단 정책과 일치해 B에서는 코드 변경이 필요하지 않았다. 녹화 필수 backpressure 자체를 제거하면 프레임 손실 또는 무제한 메모리 증가가 발생하므로 유지한다.

### C. 프리버퍼·분할·MP4 종료 분석 결과

* 압축 프리버퍼는 녹화 sink가 없을 때만 채워지고 송출 sink의 존재와 무관하다. 송출 시작·중지는 `_prebufferEnabled`, 보관 시간·메모리 제한과 기존 chunk를 변경하지 않는다.
* 녹화를 시작하면 fan-out 잠금 안에서 프리버퍼 chunk를 시간순으로 새 녹화 sink에 먼저 넣고, 이후 같은 잠금에서 활성 sink로 연결한 상태를 유지한다. 프리버퍼와 첫 실시간 chunk의 순서가 역전되지 않는다.
* 분할 녹화는 다음 MP4 process를 먼저 준비한 뒤 encoder fan-out과 같은 잠금에서 녹화 sink를 교체한다. 교체 후 chunk는 새 파일에만 들어가고 이전 MP4의 queue drain·종료·파일명 확정은 새 sink와 송출 sink를 닫지 않는다.
* 송출 시작은 기존 송출 sink만 교체하며 녹화 sink와 프리버퍼를 건드리지 않는다. 송출 중지·실패 cleanup도 녹화 process를 기다리거나 종료하지 않으며, encoder는 녹화 또는 프리버퍼가 남아 있으면 유지된다.
* MP4 종료 실패는 녹화 호출자에게 예외로 전달되고 RTMPS 실패는 정규화된 송출 상태로만 전달된다. 두 실패 경로가 상대 소비자의 성공 상태를 덮어쓰지 않는다.
* C 범위에서 순서 역전이나 송출 동작이 녹화 파일을 분할·종료시키는 결함은 발견되지 않아 코드 변경 없이 현재 불변식을 유지했다.

### D. 종료·오류 정리 결과

* 녹화 중지·분할은 MP4 queue drain과 FFmpeg 종료 결과를 호출자에게 전달하고, 송출 중지·실패는 fan-out에서 먼저 분리한 뒤 추적 cleanup으로 종료한다. 앱 종료는 두 sink와 encoder를 모두 회수하고 송출 cleanup 완료를 기다린다.
* encoder 종료 시 정상 worker 완료를 최대 12초 기다린다. 제한시간 초과로 process tree를 종료한 경우 frame writer와 encoded reader를 최대 3초 다시 기다린 뒤 남은 `Mat`, queue와 process를 Dispose하도록 보완했다. worker가 강제 종료 직후 해제된 queue·process에 접근할 수 있던 경합 구간을 줄였다.
* 송출 오류는 녹화 sink를 유지하고 공유 encoder 오류는 활성 송출에 `shared_encoder_failed`를 전달한다. 녹화 중 encoder 오류는 다음 필수 frame 처리에서 예외로 승격되어 손상 가능성을 숨기지 않는다.
* 실제 카메라가 없어 장시간 녹화 중 RTMPS 차단과 실제 MP4 탐색은 수행하지 못했다. Release 빌드·publish와 번들 FFmpeg 기능 및 정적 경계 검사를 16번 종료 검증으로 수행했다.

## 결과

* 2026-08-13: A 작업에서 `RecordingService`, 공유 H.264 encoder, 압축 프리버퍼, 녹화·송출 sink의 프레임·chunk·queue·프로세스 소유권과 종료 책임을 코드 기준으로 정리했다.
* 현재 구현은 입력 `Mat` clone, 소비자별 byte 배열 복사, 녹화·송출 sink의 독립 프로세스와 종료 경계를 갖추고 있으며 A 범위의 리소스 해제 결함은 발견되지 않았다.
* B 작업에서 녹화 필수 queue는 손실 방지 backpressure를, 송출 제한 queue는 무대기 분리 정책을 사용하며 송출 지연이 녹화 queue를 막는 경로가 없음을 확인했다.
* C 작업에서 송출 수명주기가 압축 프리버퍼, 원자적 녹화 sink 교체와 이전 MP4 마무리 경계를 변경하지 않음을 확인했다.
* D 작업에서 강제 encoder 종료 후 worker를 다시 기다린 다음 queue와 process를 해제하도록 보완했다. 실제 카메라가 필요한 동시 녹화 검증은 운영 장비 검증으로 유지한다.
