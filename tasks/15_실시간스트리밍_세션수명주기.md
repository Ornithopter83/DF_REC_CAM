# 작업명

실시간 스트리밍 세션 수명주기 안정화

## 목표

웹 시청 요청부터 DFBlackbox 명령 수신, LiveKit RTMPS 송출 시작, WebRTC 재생, 시청 중지와 lease 만료에 따른 송출 종료까지의 세션 수명주기를 일관된 상태 전이로 정리한다. 네트워크 오류나 중복 요청이 발생해도 녹화 기능과 독립적으로 안전하게 복구하거나 종료되게 한다.

## 현재 기준

* 기준 브랜치는 `스트리밍`, 기준 커밋은 `f7106e6`이다.
* `media-session` Edge Function과 006 마이그레이션으로 카메라별 Ingress, 시청 lease, 장치 명령과 송출 상태가 구현되어 있다.
* 웹은 실시간 보기·중지와 25초 lease 갱신을 수행한다.
* DFBlackbox는 3초 간격으로 명령을 폴링하고 유효한 lease가 있을 때 RTMPS 송출을 시작한다.
* LiveKit Ingress는 카메라별로 생성 후 재사용하며 기본 시청 lease는 90초다.
* 실제 카메라를 사용하는 종단 간 흐름과 장애 상황은 아직 운영 실행 환경에서 확인하고 보완해야 한다.

## 관련 영역

* DFBlackbox의 장치 명령 폴링, 카메라 상태 연결, RTMPS 송출 프로세스와 취소 처리
* Supabase `media-session` Edge Function과 카메라 스트림 세션 RPC
* 웹 포털의 LiveKit 연결, lease 갱신, 보기·중지 세션 처리
* 공유 H.264 파이프라인 중 실시간 송출 소비자 경계

## 구현 원칙

* 기존 카메라 연결·녹화·재생 동작을 보존하고 발견된 누락이나 결함만 수정한다.
* 송출 세션의 시작·중지·실패가 녹화 소비자의 큐와 파일 수명주기를 변경하지 않게 한다.
* 시작·중지·heartbeat·상태 보고는 재시도와 중복 호출에 안전한 멱등 동작으로 유지한다.
* lease가 만료되면 새 송출을 시작하지 않고 진행 중인 송출만 안전하게 종료한다.
* 장치 토큰, LiveKit API Secret, RTMPS stream key와 전체 RTSP URL을 로그나 문서에 기록하지 않는다.
* DB 스키마 변경, 새 패키지 추가, 비용이 발생하는 외부 설정 변경이 필요하면 구현 전에 영향과 이유를 보고한다.

## 세부 작업 단위

### A. 현재 세션 상태와 소유권 정리 (완료: 2026-08-13)

* 웹, Edge Function, DB RPC, DFBlackbox, FFmpeg/LiveKit 사이의 현재 호출과 상태 전이를 코드 기준으로 정리한다.
* 세션 시작·갱신·중지·만료·실패 상태에서 각 리소스의 생성자와 종료 책임자를 확인한다.
* 기존 코드로 충족되는 동작과 보완이 필요한 동작을 구분해 이후 작업의 수정 범위를 확정한다.

#### 현재 호출 흐름

1. 웹 `startLive`가 기존 `activeLive`를 정리하고 `POST cameras/{camera_id}/stream-session`을 호출한다.
2. `media-session` Edge Function이 사용자 JWT로 `request_camera_stream` RPC를 호출해 90초 `viewer_lease_until`을 만들거나 연장한다.
3. 카메라 Ingress가 없으면 Edge Function이 DB 선점 후 LiveKit RTMP Ingress를 생성하고 ID·URL·stream key를 `camera_streams`에 저장한다.
4. 웹은 5분 구독 전용 토큰으로 LiveKit Room에 연결하고 연결 완료 후 25초마다 `stream-heartbeat`을 호출한다.
5. DFBlackbox의 `DeviceStreamCoordinator`는 앱 초기화 때 한 번 생성되어 3초마다 장치 토큰으로 `stream-command`를 조회한다.
6. 유효한 lease와 Ingress가 있으면 coordinator가 최신 카메라 프레임을 복제해 `RecordingService.StartLiveStreaming`을 호출한다.
7. `SharedEncodedMediaPipeline`은 단일 H.264/MPEG-TS 인코더의 출력을 녹화 sink와 RTMPS sink에 분배한다. 첫 송출 chunk가 RTMPS sink 큐에 들어가면 `Publishing` 상태를 발생시킨다.
8. coordinator는 `Publishing` 또는 `Error` 상태를 `stream-state`로 보고한다. 시청 heartbeat가 끊기면 DB 명령과 장치의 로컬 lease 확인이 송출을 종료한다.

#### 상태와 리소스 소유권

| 영역 | 소유 상태·리소스 | 생성 책임 | 종료·정리 책임 |
| --- | --- | --- | --- |
| 웹 | `activeLive`, LiveKit `Room`, video track, heartbeat timer, `liveAttemptId` | `startLive` | `stopActiveLive`, 로그아웃·새로고침·`pagehide`, Room `Disconnected` 처리 |
| Edge Function | 요청 범위 LiveKit `IngressClient`, 참가 토큰 | `createViewerSession`, `ensureIngress` | 요청 종료 후 클라이언트 수명 종료, DB 저장에 실패한 신규 Ingress는 즉시 삭제 |
| DB | 카메라별 Ingress 정보, `viewer_lease_until`, `state`, 마지막 폴링·시작·중지 시각 | `request_camera_stream`, Ingress 완료 RPC | lease 만료 후 다음 장치 명령 조회가 `requested/publishing`을 `idle`로 전환하며 Ingress 자체는 재사용을 위해 유지 |
| DFBlackbox | 단일 폴링 루프, 활성 camera/Ingress/lease, 마지막 보고 상태 | `MainForm.InitializeApp`에서 coordinator 생성·`Start` | coordinator `DisposeAsync`가 폴링 취소·이벤트 해제·송출 중지·HTTP client 해제 |

| 미디어 파이프라인 | FFmpeg H.264 인코더, MP4 sink, RTMPS sink, 각 큐와 작업 | `RecordingService`가 필요 시 `SharedEncodedMediaPipeline` 생성 | 녹화와 송출 sink를 독립 정리하고 소비자가 없을 때 인코더 종료, 앱 종료 시 `RecordingService.Dispose` |

#### 현재 코드로 충족되는 경계

* coordinator `Start`는 단일 `_loop`만 만들고 앱 종료 시 루프를 기다린 뒤 HTTP client까지 해제한다.
* 장치 토큰과 RTMPS stream key는 저장하거나 정상 로그에 출력하지 않는다. 로그의 카메라 식별자는 앞 8자리만 사용한다.
* 최신 프레임은 잠금 안에서 복제·교체되며 송출 시작용 복제본도 호출 범위에서 해제된다.
* 녹화 sink는 필수 큐, RTMPS sink는 제한된 비필수 큐를 사용해 느린 송출이 녹화 fan-out을 역압하지 않는다.
* RTMPS 실패는 해당 sink를 파이프라인에서 분리하며, 녹화 sink와 공유 인코더는 녹화가 진행 중이면 유지한다.
* 웹의 새 시청 시작, 새로고침, 로그아웃과 페이지 이탈은 기존 Room 및 heartbeat를 정리한다.
* DB의 Ingress 생성 선점과 생성 후 저장 실패 시 재조회·고아 Ingress 삭제 경계가 구현되어 있다.

#### 후속 작업에서 보완할 경계

* B: `report_camera_stream_state`는 lease 만료 또는 더 최신 상태와 무관하게 늦게 도착한 `publishing/error` 보고를 수용한다. 동시 Ingress 준비 요청도 즉시 409로 끝나므로 재조회·멱등 응답 범위를 확인해야 한다.
* C: 폴링 루프와 `StreamingStatusChanged` 보고 작업이 활성 세션 필드와 마지막 보고 상태를 완전히 직렬화하지 않는다. 상태 HTTP 요청의 완료 순서가 뒤집히거나 이전 상태 보고가 새 상태를 덮는지 모의 응답으로 확인해야 한다.
* D: RTMPS sink 종료는 fire-and-forget 작업으로 수행되어 `StopLiveStreaming` 반환 시 실제 FFmpeg 종료 완료를 보장하지 않는다. 상태 이벤트에도 세션 세대 식별자가 없어 이전 송출의 늦은 이벤트를 구분할 수 없다.
* E: 송출 sink가 오류 상태가 되면 유효 lease 동안 다음 3초 폴링에서 다시 시작한다. 네트워크 장기 장애 시 재시도 간격과 만료 후 재시작 방지 정책을 보완해야 한다.
* F: 웹의 `보기 중지`는 Room과 heartbeat만 중지하며 서버에 명시적인 종료를 전달하지 않는다. 다른 시청자가 없더라도 기존 lease가 끝날 때까지 최대 약 90초간 장치 송출이 유지될 수 있다. 즉시 중지 계약은 DB/API 변경 영향을 먼저 보고한 뒤 별도 지시에 따라 결정해야 한다.
* F: heartbeat 실패 후에도 웹은 25초 재시도를 계속하고 Room 연결을 유지한다. lease가 만료되어 장치 송출이 끝난 상태와 사용자 화면 상태를 일치시키는 처리가 필요하다.
* G: 현재 정상 로그에는 비밀값이 없지만 예외·프로세스 진단 경로까지 포함한 전체 민감정보 노출 검사는 별도로 수행해야 한다.
* H: 실제 FFmpeg 종료 시간, LiveKit 트랙 게시·해제, 카메라 닫기·재열기와 녹화 동시 동작은 실제 카메라 환경에서 확인해야 한다.

### B. 서버 세션 명령의 멱등성과 상태 전이 보완 (완료: 2026-08-13)

* 동시 시청 시작, 반복 heartbeat, 중복 중지 요청이 단일 카메라 세션을 일관되게 갱신하는지 확인하고 필요한 부분만 보완한다.
* Ingress 생성 선점, DB 저장 실패 후 정리, 기존 Ingress 재사용의 상태 전이를 명확히 한다.
* 인증·권한·누락·충돌·외부 서비스 실패가 정의된 API 오류로 반환되게 한다.

#### 구현 결과

* `202608130008_stream_session_state_guards.sql`을 추가해 기존 `report_camera_stream_state` 함수의 서명과 실행 권한은 유지하면서 상태 갱신을 행 잠금 안에서 판정하게 했다.
* lease가 만료된 뒤 도착한 `publishing/error` 보고는 세션을 되살리지 않고 DB 상태를 `idle`로 정규화한다.
* 유효한 새 lease가 만들어진 뒤 이전 명령의 `idle` 보고가 늦게 도착하면 해당 보고를 거부해 새 `requested/publishing` 상태를 중지시키지 않는다.
* 활성 lease 안의 `publishing/error` 보고는 허용해 동일 lease에서 장치가 송출 오류 후 재시작할 수 있는 기존 동작을 보존했다. 같은 활성 lease 안에서 이전 송출과 새 송출을 완전히 구분하려면 장치 보고 세대가 필요하므로 C·D의 직렬화 범위에서 다룬다.
* 동시 요청이 이미 Ingress 생성을 선점한 경우 Edge Function이 250ms 간격으로 최대 5초간 구성을 재조회한다. 선행 요청이 완료되면 같은 Ingress를 재사용하고, 오류가 확정되면 502, 제한 시간 동안 계속 준비 중이면 기존 409를 반환한다.
* DB의 `operation_not_authorized` 오류를 502가 아니라 명시적인 403 API 응답으로 변환하도록 보완했다.
* 새 마이그레이션은 로컬 파일로만 추가했으며 원격 DB 적용과 `media-session` 재배포는 수행하지 않았다.

### C. DFBlackbox 명령 폴링 수명주기 보완 (완료: 2026-08-13)

* 앱 시작, 기기 등록·해제, 카메라 열기·닫기와 폴링 작업의 시작·취소 순서를 정리한다.
* 일시적 네트워크 오류에서 중복 폴러가 생성되지 않고 제한된 간격으로 재시도하게 한다.
* 오래된 응답이나 취소 이후 도착한 응답이 새 세션 상태를 덮어쓰지 않게 한다.

#### 구현 결과

* 기존 `_loop ??=` 단일 폴러 구조는 유지하고, 폴링 응답 처리·publisher 상태 변경·비동기 상태 보고를 하나의 `SemaphoreSlim` 직렬화 경계로 묶었다.
* 폴링 시작 시 장치 ID·카메라 ID·장치 토큰·설정 revision을 묶은 컨텍스트를 만들고 HTTP 응답 후 다시 확인한다. 요청 중 등록 정보나 DPAPI 토큰이 바뀌면 해당 응답을 폐기하고 기존 publisher를 정리한다.
* 등록 완료와 등록 해제 시 `MainForm`이 coordinator에 변경을 알린다. 현재 HTTP 요청과 폴링 대기를 깨워 같은 단일 루프가 즉시 새 설정을 평가하며 별도 폴러는 만들지 않는다.
* 활성 publisher가 시작될 때 사용한 장치 ID와 토큰을 해당 publisher의 메모리 수명에만 보관한다. 비동기 상태 보고가 토큰 파일의 새 값을 다시 읽어 이전 publisher 상태를 새 등록으로 보고하지 않게 했다.
* publisher generation과 현재 파이프라인 상태를 함께 확인해 중지·교체 이후 대기 중이던 `Publishing/Error` 보고를 폐기한다. 같은 활성 파이프라인 내부의 이벤트 세대 구분은 D에서 파이프라인 경계와 함께 처리한다.
* 마지막 상태 비교와 상태 HTTP 호출도 직렬화해 동일 상태의 중복 전송과 완료 순서 역전을 방지했다.
* 상태 보고 작업을 추적하고 앱 종료 시 폴링 취소, 이벤트 구독 해제, publisher 정리, 대기 중 보고 완료 순으로 종료한다.
* 카메라 닫기는 기존 `SuspendLiveStreaming`이 즉시 송출 sink를 분리하고, 이후 폴링은 최근 프레임이 없으면 `camera_frame_unavailable`만 보고하는 기존 경계를 유지했다.

### D. RTMPS 송출 시작·중지 수명주기 보완 (완료: 2026-08-13)

* 동일 카메라에 대해 송출 프로세스가 중복 시작되지 않게 한다.
* 시청 시작, 시청 중지, lease 만료, 카메라 닫기, 앱 종료, 송출 실패의 종료 경로를 하나의 안전한 정리 흐름으로 수렴시킨다.
* 프로세스, 스트림, 취소 토큰과 큐의 소유권 및 Dispose 시점을 확인한다.

#### 구현 결과

* `SharedEncodedMediaPipeline`에 단조 증가하는 송출 세대를 추가하고 모든 `Starting/Publishing/Error/Idle` 상태에 해당 세대를 포함했다. 기존 상태 생성자에는 선택 속성만 추가해 호출 호환성을 유지했다.
* coordinator는 publisher 시작 후 파이프라인 송출 세대를 보관하고 자체 publisher generation과 함께 검사한다. 이전 RTMPS sink에서 늦게 전달된 상태 이벤트는 상태 값이 우연히 같더라도 새 publisher의 서버 상태로 보고되지 않는다.
* 새 RTMPS sink를 시작할 때 기존 sink를 먼저 파이프라인에서 분리하고 실제 FFmpeg 프로세스와 writer 작업의 종료를 기다린 다음 새 sink를 생성한다. 같은 stream key를 사용하는 이전 프로세스와 새 프로세스가 겹치는 구간을 제거했다.
* 정상 중지, lease 만료, 카메라 닫기, 앱 종료, 송출 큐 포화, 공유 인코더 실패가 모두 동일한 `CloseStreamingSink` 경계에서 입력 종료·프로세스 종료·큐·프로세스 Dispose를 수행한다.
* RTMPS 종료 작업은 파이프라인이 추적한다. 네트워크 실패 콜백에서는 공유 인코더 출력 읽기와 녹화를 막지 않도록 비동기로 정리하고, coordinator의 명시적 중지·교체·종료는 추적된 작업 완료를 기다린다. 정상 종료를 최대 15초 기다리고, 제한시간 초과 시 프로세스 트리를 종료한 뒤 writer 작업을 최대 3초 더 확인한다.
* 녹화 sink는 기존 필수 큐와 별도 수명주기를 유지한다. RTMPS sink 교체·실패·종료는 녹화 sink를 닫거나 공유 인코더를 중단하지 않으며, 인코더는 녹화·송출·프리버퍼 소비자가 모두 없을 때만 종료된다.
* 실제 카메라와 LiveKit 연결이 없어 FFmpeg RTMPS 정상 종료 시간과 원격 트랙 해제는 H의 운영 검증으로 남겼다.

### E. lease 만료와 네트워크 장애 복구 구현 (완료: 2026-08-13)

* 웹 heartbeat 중단 후 서버 lease 만료와 장치의 송출 종료가 확정적으로 이어지게 한다.
* Edge Function 또는 LiveKit 연결이 일시적으로 끊겼을 때 녹화를 유지하면서 송출만 재시도하거나 종료한다.
* 복구 시 만료된 명령으로 재송출하지 않고 현재 유효한 lease를 다시 확인한다.

#### 구현 결과

* `should_stream=true` 명령도 `lease_until`이 없거나 장치의 현재 UTC 시각보다 이전이면 실행하지 않고 기존 publisher와 재시도 상태를 정리한다. HTTP 지연 뒤 도착한 만료 명령이 송출을 다시 시작하지 않는다.
* RTMPS 시작 실패, 송출 sink 오류와 공유 인코더 오류를 같은 송출 대상(camera ID·Ingress URL·stream key)별로 집계한다.
* 실제 FFmpeg publisher 재시도는 3초에서 시작해 실패할 때마다 6·12·24초로 늘리고 최대 30초로 제한한다. 동일 publisher 세대의 이벤트와 다음 폴링이 같은 실패를 중복 집계하지 않게 했다.
* backoff 중에도 3초 장치 명령 폴링은 유지한다. 새 heartbeat로 갱신된 lease, 시청 종료와 등록 변경을 계속 확인하되 backoff 시각 전에는 FFmpeg만 다시 시작하지 않는다.
* RTMPS가 `Publishing`에 도달하면 실패 횟수와 다음 시도 시각을 초기화한다. lease 만료, `should_stream=false`, 등록 완료·해제, 인증 거부와 카메라 등록 불일치에서도 이전 재시도 상태를 제거한다.
* 명령 폴링 네트워크 오류 중에는 현재 publisher를 즉시 끊지 않고 로컬에 마지막으로 받은 lease까지 유지한다. 대기시간은 남은 lease보다 길어지지 않으며 로컬 만료 시 녹화와 분리해 송출만 종료한다.
* 재시도 로그에는 대기시간과 축약 카메라 ID만 기록하고 Ingress URL과 stream key는 출력하지 않는다.
* 실제 네트워크 차단 후 LiveKit 복구 시간과 원격 트랙 재게시 여부는 카메라가 필요한 H 운영 검증으로 남겼다.

### F. 웹 시청 세션 처리 보완 (완료: 2026-08-13)

* 보기·중지·페이지 이탈·카메라 변경 시 heartbeat와 LiveKit Room 연결을 한 세션 단위로 정리한다.
* 반복 클릭과 연결 지연 중 상태 변경이 중복 lease 또는 남은 연결을 만들지 않게 한다.
* 사용자에게 필요한 연결 중·재생 중·종료·실패 상태만 노출하고 비밀값이나 내부 경로는 표시하지 않는다.

#### 구현 결과

* 웹의 실시간 보기는 한 번에 하나의 활성 세션만 유지한다. 새 카메라 보기, 중지, 로그아웃, 새로고침과 페이지 이탈 시 진행 중인 세션 생성 요청과 heartbeat 요청을 취소하고 LiveKit Room과 트랙을 정리한다.
* 연결 시도 번호와 활성 세션 객체를 함께 검사해 이전 요청의 늦은 응답, 이전 Room의 트랙 이벤트와 중복 클릭이 새 세션의 UI나 lease를 변경하지 못하게 했다.
* 서버가 반환한 `lease_until`을 웹에서도 추적한다. heartbeat 실패 시 남은 lease 안에서만 재시도하며 다음 대기시간이 lease 만료를 넘지 않게 제한하고, 로컬 만료 후에는 heartbeat를 다시 보내 lease를 되살리지 않고 Room을 종료해 재연결이 필요함을 표시한다.
* 보기 중지는 웹의 Room과 heartbeat를 즉시 끝낸다. 서버 lease는 카메라 단위의 합산 lease이므로 개별 브라우저가 즉시 서버 lease를 취소하면 다른 시청자의 송출까지 중단할 수 있어 별도 취소 API는 추가하지 않았다. 마지막 시청자의 heartbeat가 멈춘 뒤 기존 90초 lease가 만료되면 장치 송출이 종료된다.
* DB 스키마, Edge Function API와 패키지는 변경하지 않았고 사용자 화면이나 오류 메시지에 LiveKit 참가 토큰과 내부 연결 정보를 추가하지 않았다.

### G. 운영 로그와 오류 경계 정리 (완료: 2026-08-13)
